# Native branch query performance gate

This opt-in benchmark compares the existing adapter `queryDrafts` operation, the native effective-projection query, and the guarded core `queryBranchContentGraph` operation, including its native fixed snapshot and raw graph collection at depth zero. The core measurement includes scope readiness and freshness checks, original collection read access, logical query compilation, native execution, generation validation, and decoding. Application document hooks run after this internal boundary and are absent from all three measurements. The actor has the same collection access predicate (`ordinal >= 0`), page size 20 and page one. Inherited English workloads use identical logical filters and ordering. A separate French workload filters and sorts the actual owned `-review` values and asserts its membership equals the override count. Legacy latest revisions have exactly the same composed localized status maps and content as the effective branch, including published inherited locales and the owned French draft locale.

The baseline executes this repository's existing adapter path on the same source and dataset; it does not run an immutable released npm binary or a public transport benchmark.

The ordinary integration suite skips the benchmark unless `PAYLOAD_BRANCH_PERF=true`. The benchmark uses the shared integration fixture lifecycle. It requires a dedicated disposable database: the fixture drops its configured database before seeding. Do not point these commands at an application database.

## Matrix and data

Run every combination of 10,000 and 100,000 logical documents, 1% and 80% branch override density, two and ten locales, and one and twenty working branches on SQLite, Postgres, and MongoDB. There is an additional `main` projection in every case. Every working branch has the same deterministic override distribution; this controls comparison values while measuring the real storage and maintenance costs of a populated branch catalog.

Ordinary content anchors keep their logical IDs and materialized published values. Each document has one frozen main revision and one legacy latest draft with the selected branch's composed effective values. Overridden documents have one additional frozen revision; their French locale head selects that revision on every working branch. Every document has real main shared and locale heads. The other branch scopes inherit main. Head references and pin records use real revision IDs and generations.

One percent of logical documents have a section block, four nested array items, three child items per item, and 32 relationship edges, including a self-cycle and 31 other targets. Remaining documents have one relationship edge and no nested body. The heavy subset is deliberately included in the overridden subset, so these distributions are correlated. That same one-percent subset has 100 additional historical revisions, including real localized nested rows and relationships. This is a representative mixed workload, not a claim that every document has the heavy shape or long history.

Bulk fixture startup deliberately bypasses per-document hooks, CAS mutation, and incremental projection maintenance. It uses the actual Mongo and Drizzle write transforms and the same sanitized collection schemas as normal writes. All effective cache bodies are generated with the production scope compiler, scope composer, and projection codec from the exact authoritative version/head selections being loaded. Cache and head/root counts and query parity are checked before timing. Scope readiness is initialized through the real transaction-aware control helpers only after loading finishes. Before timing, the complete decoded cache bodies with `locale: all`, including every configured locale, of four representative logical documents (record zero, record one, the center heavy record, and the last record) are retained on main and every working branch. Those identities are then rebuilt from the actual native heads and versions through production `rebuildBranchProjection`, inside one real caller transaction. Every rebuilt body must strictly equal its retained pre-rebuild body, including property presence and null values; rebuilding cannot silently repair a faulty bulk seed before parity is checked. The common heavy input explicitly supplies the native built-in `blockName: null` to both frozen version and cache composition inputs. The separately reported rebuild milliseconds cover native rebuild and commit; `verificationCalls` includes the before and after verification reads as well. This proof validates native hydration and derived write formats without claiming the bulk population used incremental maintenance. An additional opt-in `fixture-parity.int.spec.ts` uses the same shared fixture and verification helpers with 200 logical documents, and checks complete heavy-body equality against native legacy drafts in English and French without running timed workloads. It also corrupts a non-English cached title and requires the before/after authority comparison to reject the drift even though rebuilding repairs the cache; expected values for every configured title locale are checked explicitly. Native SQL `ANALYZE` runs after bulk loading so comparison plans use real fixture statistics. Separately measured ordinary-body and heavy-body post-load main-head changes use the actual version initialization, head CAS, transaction commit, and automatic branch fanout maintenance; their resulting content is checked through the guarded query operation.

## Reproduction

Use Node 24.15.0 or later. Services must already be running. Example isolated local services used during implementation are Postgres on port 55439 and a Mongo replica set named `branchHeads` on port 27439. Create a dedicated empty Postgres database `payload_branch_perf` first.

```sh
PAYLOAD_BRANCH_PERF=true PAYLOAD_BRANCH_PERF_DOCUMENTS=10000 \
PAYLOAD_BRANCH_PERF_LOCALES=2 PAYLOAD_BRANCH_PERF_BRANCHES=1 \
PAYLOAD_BRANCH_PERF_DENSITY=0.01 PAYLOAD_DATABASE=sqlite \
SQLITE_URL=file:/private/tmp/payload-branch-perf.db \
node_modules/.bin/vitest run --project int \
test/version-branches/performance/query-performance.int.spec.ts
```

For Postgres set `PAYLOAD_DATABASE=postgres` and `POSTGRES_URL=postgres://payload@127.0.0.1:55439/payload_branch_perf`. For Mongo set `PAYLOAD_DATABASE=mongodb` and `MONGODB_URL=mongodb://127.0.0.1:27439/payload_branch_perf?directConnection=true&replicaSet=branchHeads`. Use the same four scenario variables for each combination. To run all sixteen diagnostic scenarios for one adapter sequentially, set its dedicated database URL and run `node test/version-branches/performance/runMatrix.mjs sqlite` (or `postgres` / `mongodb`). The runner stops at the first failed gate by default; `PAYLOAD_BRANCH_PERF_CONTINUE_ON_FAILURE=true` gathers the remaining diagnostic scenarios while retaining a failing exit status. Run adapter processes sequentially: the repository test setup regenerates a shared adapter module even when the databases are isolated.

A depth-two raw forward graph workload selects 20 heavy roots, follows 32 relationships per root, preserves self-cycles, and applies an access predicate denying 20 referenced documents. It compares the real branch graph collector with existing native draft reads using the same bounded breadth-first batches and policy. The latter is an explicit raw adapter baseline; it does not claim to be the public population pipeline. Every collected coordinate is checked against the baseline, denied targets must be explicit null, and unknown coordinates must fail closed. Native snapshot trace/resource failures are failures of this workload and remain in the evidence. Public hooks and population remain separate later-phase gates.

Final evidence is explicitly separated from diagnostics. Add `PAYLOAD_BRANCH_PERF_EVIDENCE=final` when invoking `runMatrix.mjs`; the runner computes and pins the complete implementation/harness SHA-256 before spawning any scenario. Every scenario verifies the source still matches at completion. Artifacts and matrix manifests are grouped under `<output>/<diagnostic-or-final>/<source-digest>/`, so pre-fix measurements cannot satisfy final coverage. Reports include the native database version, Node/OS/CPU architecture, CPU model/count, total RAM, starting load average, Git HEAD, and a read-only dirty-status check. Source hashing includes new/uncommitted implementation files, the benchmark, package manifests, dependency lockfile, shared integration helpers and test configuration. The generated adapter module is excluded because each adapter run regenerates it; its producer and the selected native adapter are recorded. Format and lint all source before freezing final measurements, since formatting changes correctly invalidate the digest. Final runs require settled source and a coordinated quiet timing window. The matrix pins both source digest and Git HEAD, rejects any hashed input that is untracked or differs from that commit, and verifies both before seeding, across scenarios, and at completion. Unrelated dirty user files are allowed and reported. The summary accepts a later generated-evidence-only commit when all hashed inputs still match the shared measurement commit.

Run `node test/version-branches/performance/writeResults.mjs` after measurements to update the tracked [compact coverage table](./performance/RESULTS.md) and [representative native plans](./performance/NATIVE-PLANS.md). The coverage table only accepts explicit final reports for the current exact source digest and includes each measured layer's p50/p95, calls and ordinary/heavy maintenance latency. `PAYLOAD_BRANCH_PERF_REQUIRE_COMPLETE=true` makes this summary command fail if any of the 48 required scenarios is missing or failed. Seed-start manifests and progress log records retain phase, inserted rows/calls, elapsed time and RSS during large fixture loading.

The native-plan artifact samples the smallest and largest available unchanged-source final scenario per adapter. It retains statement and raw-report SHA-256 fingerprints, actual winning/index plan choices, Mongo cursor and lookup counters, and PostgreSQL scan rows per loop and buffers. It labels unavailable counters explicitly and never adds overlapping plan-node counters into a fabricated rows-examined total. SQLite provides plan/index choices only. To retain earlier failures for review, pass repeated `--diagnostic-report <path-to-retained-json>` arguments to the writer; those reports appear in a clearly labeled historical section and never count as final coverage. Full native statements, explanations, samples, and CPU profiles remain local. Generated `RESULTS.md`, `NATIVE-PLANS.md`, and measurement output directories are excluded from source hashing; benchmark JSON configuration and other source documents are included.

Each workload has five warmups and forty measured runs by default. `PAYLOAD_BRANCH_PERF_ITERATIONS` can increase the sample count. Final runs require an integer of at least forty; the result writer independently verifies that every scalar and graph layer retained the requested samples. Diagnostics may explicitly use fewer samples and cannot satisfy final coverage. Machine-readable reports are written under `/private/tmp/payload-branch-performance`, or `PAYLOAD_BRANCH_PERF_OUTPUT`. Reports include ordinary published queries through the original adapter path, database storage size, and retain individual timing samples, nearest-rank p50/p95, native client calls for a representative operation, per-sample Mongo wire latency sums, native query explanations, process memory before and after each sample group, and measured maintenance statements and latency, native acknowledged affected rows, and storage after each mutation. Affected rows count normalized SQL rows or Mongo documents reported by the native write replies; Mongo find-and-modify reports matched rows and may include a no-op. This is an explicit logical/normalized write-amplification metric, not a measurement of WAL/oplog or storage-device bytes. Every affected branch body is checked after the timed mutation. Mongo command duration sums may overlap when an adapter launches parallel operations and are subject to driver timing resolution; they are not subtracted from wall time to infer JavaScript cost. Postgres explanations include actual rows and buffers; Mongo explanations include execution statistics. SQLite `EXPLAIN QUERY PLAN` describes index/scan choices and does not expose an actual rows-examined count.

A separate selective-query diagnostic pass attributes snapshot setup, native guard reads, collection access callbacks, remaining callback time, and cleanup. After the native read facade became opaque, diagnostics stopped mutating scoped methods; native projection timing comes from the separate native layer and CPU profiles, while callback-after-guard timing includes query execution, decode and graph work. These wrappers are absent from gated timings. `PAYLOAD_BRANCH_PERF_PROFILE=true` also writes a CPU profile from the actual integration worker, after timed measurements.

The test asserts parity before measuring. It then asserts guarded-core p50 and p95 at most twice the equivalent current-draft native percentiles for each measured workload. Evidence remains on disk if parity or the budget fails. A failure is a design or implementation gate that must be fixed or explicitly reviewed as a bounded exception; native-only timings cannot substitute for guarded-core timings.

## Evidence status

Distribution and percentile helper tests pass. The first real SQLite scenario (10,000 documents, two locales, one working branch, 1% overrides) passed authoritative counts/references, representative complete decoded content, all four query parity checks, and real main-head maintenance. Loading produced 1,169,800 physical rows in 19.2 seconds, 30,100 heads and pins, and approximately 138 MiB of SQLite data. The measured main-head change took 27.1 ms, 122 native client statements, and 62 write statements for main plus one working branch.

The query performance gate **failed** in this initial implementation:

| Workload               | Current drafts native p95 | Native branch p95 | Guarded core p95 | Core/drafts |
| ---------------------- | ------------------------: | ----------------: | ---------------: | ----------: |
| Indexed selective page |                   1.20 ms |           1.63 ms |          2.20 ms |       1.83x |
| Range page and total   |                   4.65 ms |          50.67 ms |         52.28 ms |      11.24x |
| Relationship predicate |                  16.17 ms |         161.54 ms |        163.45 ms |      10.11x |
| Nested block predicate |                  10.48 ms |          57.25 ms |         68.14 ms |       6.50x |

These are forty warm samples from the local Node 24.15.0 macOS arm 64 environment. The raw JSON with individual samples and native plans is `/private/tmp/payload-branch-performance/sqlite-10000-2-1-0.01-initial-failure.json`; log: `/private/tmp/payload-branch-performance/sqlite-10000-2-1-0.01-initial-failure.log`. These measurements are diagnostic evidence, not a passing scale matrix or a release benchmark.

SQLite `EXPLAIN QUERY PLAN` shows the grouped, ranked effective ID relation repeated in the page selection, total, and scalar ordering subqueries. Each repeats root scans and temporary sorting. Root branch, visibility, and access restrictions live in a correlated self-table `EXISTS`, which prevents the outer relation from driving directly from the branch indexes. Native branch execution already accounts for nearly all of the regression; removing guard checks would not address it. The implementation changed root restrictions into driving predicates and materialized the shared ranked ID relation once per native statement. The repeated scenario passed all parity and maintenance assertions and produced the following guarded-core p95 values:

| Workload               | Current drafts native p95 | Guarded core p95 | Core/drafts |
| ---------------------- | ------------------------: | ---------------: | ----------: |
| Indexed selective page |                   1.33 ms |          1.76 ms |       1.32x |
| Range page and total   |                   4.57 ms |          8.53 ms |       1.87x |
| Relationship predicate |                  15.85 ms |         25.40 ms |       1.60x |
| Nested block predicate |                  10.89 ms |         10.17 ms |       0.93x |

This passing diagnostic predates the required native snapshot, graph boundary, and owned-locale workload. It cannot establish the final gate. The rerun evidence is `/private/tmp/payload-branch-performance/sqlite-10000-2-1-0.01.json`. Native branch find used one client statement; the guarded core used three. The ordinary published query used the original collection path and remained separate. The rest of the matrix is required before M3 can close.

Mongo diagnostics exposed a relationship query that examined a filtered target set separately for each source row. Native equality lookups reduced examined targets but retained substantial per-root work. The implementation now starts eligible positive relationship predicates at the selective target collection and uses an indexed reverse equality lookup into roots; general predicates retain the guarded fallback. A quiet final-snapshot 10k run passed every scalar p95 comparison, including the owned French predicate. It still failed the selective p50 comparison: 1.842 ms versus 0.850 ms (2.167x). Its selective p95 was 2.096 ms versus 1.230 ms (1.705x). A separate diagnostic attributed median selective time to native snapshot setup 0.195 ms, guard reads 0.603 ms, native projection 0.606 ms, access callbacks 0.002 ms, remaining callback work 0.373 ms, and cleanup 0.007 ms. The earlier 9.67 ms selective measurement did not reproduce in this quiet window. The actual integration-worker CPU profile contains 87 idle samples out of 242; raw graph collection and decoding are the largest individual JavaScript leaves.

The same run passed full raw graph parity for 660 coordinates, including 20 denied targets and self-cycles. It failed the depth-two graph performance budget: native legacy BFS p50/p95 were 10.237/10.810 ms; guarded branch graph 29.459/36.460 ms (2.878x/3.373x). The branch graph issued 46 commands compared with 16 for legacy raw BFS, because each target batch repeats readiness and generation guards. Evidence is retained as `mongodb-10000-2-1-0.01-snapshot-graph-failure.json` and its adjacent log. These are real failures requiring a fix; neither the scalar p95 results nor native-only timings establish completion. Guard reuse, remembering each graph target once, and consuming freshly owned native rows during decoding improved the next Mongo diagnostic to graph p50/p95 ratios 2.135x/2.263x, still failing. All five scalar percentile comparisons, authoritative hydration samples and both native caller/fresh snapshot graph parity passed. Its profile identified schema traversal as the largest remaining JavaScript work; this is retained as an optimization diagnostic, not final evidence.

The first Postgres diagnostic did not analyze bulk-loaded tables; its relationship baseline plan was unrepresentative. Its result is preserved as `postgres-10000-2-1-0.01-no-analyze-diagnostic.json` and does not establish a performance gate. The analyzed rerun with the final native snapshot and operation-local guard reuse passed all parity checks, the 660-coordinate graph, and its default-caller-transaction graph proof. The graph used 18 commands versus 16 for the existing raw BFS and passed both percentile budgets (p50 ratio 1.846x, p95 ratio 1.799x). The no-join range page still failed: existing native draft p50/p95 were 2.639/2.737 ms versus 6.239/6.654 ms for the complete branch operation. Actual native SQL dominated: it grouped, sorted, and window-ranked all 5,000 matching rows before sorting the materialized relation again for the page. Its native-only p50 was 5.164 ms. Evidence is preserved as `postgres-10000-2-1-0.01-analyzed-range-failure.json` and its adjacent log. This remains an unresolved gate.

The complete native scale matrix remains pending; no performance exception has been approved. Hosted Vercel/Neon and D1 transport limits require separate release validation. Local service measurements do not establish hosted latency or transport budgets.
