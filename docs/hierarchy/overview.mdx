Hierarchy lets you nest documents within a collection and generate paths for URLs and breadcrumbs. [Folders](../folders/overview) and [Tags](../tags/overview) use the same hierarchy system, with defaults for organizing content and building taxonomies.

| Configuration | Use it for                                               | Relationships from other collections                      |
| ------------- | -------------------------------------------------------- | --------------------------------------------------------- |
| `hierarchy`   | Nested pages, categories, or a custom content structure. | Configure relationship fields for your use case.          |
| `folders`     | Grouping documents into folders.                         | Single-folder assignment through `createFolderField`.     |
| `tags`        | Taxonomies, including nested tags or categories.         | Multiple assignments by default through `createTagField`. |

Set one of `hierarchy`, `folders`, or `tags` on the collection that defines the structure. These options cannot be enabled together on the same collection. Other collections can reference that structure through relationship fields. A content collection can have both a folder field and a tag field, referencing separate collections.

<Banner type="info">
  Folders still exist in Payload 4. They use the hierarchy foundation instead of
  the global folder configuration from Payload 3. See the [migration
  guide](../migration-guide/v4#folders-use-the-hierarchy-foundation) when
  upgrading an existing project.
</Banner>

## Quick Start

Enable hierarchy on a collection to nest its documents under other documents in that same collection:

```ts
import type { CollectionConfig } from 'payload'

export const Pages: CollectionConfig = {
  slug: 'pages',
  admin: {
    useAsTitle: 'title',
  },
  fields: [
    {
      name: 'title',
      type: 'text',
      required: true,
    },
  ],
  hierarchy: {
    parentFieldName: 'parent',
  },
}
```

Payload adds a single, non-localized `parent` relationship to `pages`, along with virtual `_h_slugPath` and `_h_titlePath` fields. Setting `hierarchy: true` uses the default parent field name, `_h_pages`.

A hierarchy's parent relationship is always self-referential: a page nests under another page, a folder under another folder, and a tag under another tag. References from other collections assign content to hierarchy items; they do not change the hierarchy's parent relationship.

## Configuration

Pass `true` for defaults or an object to customize the hierarchy:

| Option                       | Description                                                                                                                                                                                                                                                    |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parentFieldName`            | Name of the parent relationship field. `hierarchy: true` defaults to `_h_<collectionSlug>`. Specify this when using an object.                                                                                                                                 |
| `allowHasMany`               | Whether related fields allow multiple assignments when they omit `hasMany`. Defaults to `true`. The hierarchy's own parent field always has `hasMany: false`.                                                                                                  |
| `collectionSpecific`         | Allow hierarchy items to restrict which related collections they accept. Defaults to `false`. Use `true` for a `hierarchyType` select field, or `{ fieldName: 'allowedTypes' }` for a custom name.                                                             |
| `joinField`                  | Add a join field for direct children and related content, e.g. `{ name: 'children' }`. No join field is added by default. Supports additional [Join Field](../fields/join) options, except the generated `type`, `collection`, `on`, and `hasMany` properties. |
| `slugField`                  | Existing field whose value supplies each slug path segment. When omitted, Payload slugifies the title from `admin.useAsTitle`.                                                                                                                                 |
| `slugify`                    | Custom function for converting titles to slug path segments. Used when `slugField` is not set.                                                                                                                                                                 |
| `slugPathFieldName`          | Name of the virtual slug path field. Defaults to `_h_slugPath`.                                                                                                                                                                                                |
| `titlePathFieldName`         | Name of the virtual title path field. Defaults to `_h_titlePath`.                                                                                                                                                                                              |
| `admin.injectSidebarTab`     | Add a sidebar tab for browsing this hierarchy. Defaults to `true`.                                                                                                                                                                                             |
| `admin.treeLimit`            | Maximum number of items to load in tree views. Defaults to `100`.                                                                                                                                                                                              |
| `admin.useHeaderButton`      | Choose whether to select a parent through a header button or an inline field.                                                                                                                                                                                  |
| `admin.components.Icon`      | Custom icon for hierarchy items.                                                                                                                                                                                                                               |
| `admin.components.SmallIcon` | Custom icon for smaller hierarchy views. Falls back to `Icon`. Available on `hierarchy`; the folder and tag presets expose `Icon`.                                                                                                                             |

### With a Custom Parent Field

Define the parent field yourself when you need custom field options. It must be a single, non-localized relationship to the same collection:

```ts
import type { CollectionConfig } from 'payload'

export const Categories: CollectionConfig = {
  slug: 'categories',
  admin: {
    useAsTitle: 'name',
  },
  fields: [
    {
      name: 'name',
      type: 'text',
      required: true,
    },
    {
      name: 'parentCategory',
      type: 'relationship',
      relationTo: 'categories',
      hasMany: false,
      localized: false,
      admin: {
        position: 'sidebar',
      },
    },
  ],
  hierarchy: {
    parentFieldName: 'parentCategory',
  },
}
```

## Connecting Other Collections

Use `createFolderField` or `createTagField` from `payload` to connect a content collection to a hierarchy collection. These helpers generate a relationship field named `_h_<hierarchyCollectionSlug>`. If the hierarchy sets a custom `parentFieldName`, Payload renames the related field to match when it prepares your config.

For example, a `folders` collection with `folders: true` can organize both pages and media. Add `createFolderField({ relationTo: 'folders' })` to each content collection's `fields` array. The folders form their own tree, and pages and media reference folders in that tree.

See [Folders](../folders/overview) and [Tags](../tags/overview) for complete configurations and helper options.

### Restricting Accepted Collections

Set `collectionSpecific: true` on the hierarchy to let editors choose which related collections each item accepts. Payload adds a `hierarchyType` select field with an option for each collection connected through a hierarchy field. An empty selection allows all related collections.

### Querying Direct Children

Set `joinField: { name: 'children' }` to add a join across the hierarchy collection and its related collections. This returns direct children and assigned documents, rather than every descendant in the tree. Configure pagination and population as you would for other [Join Fields](../fields/join).

## Auto-Generated Fields

Hierarchy adds two virtual text fields. They are computed when requested and are not stored in the database:

| Field          | Example                    | Source                                                             |
| -------------- | -------------------------- | ------------------------------------------------------------------ |
| `_h_slugPath`  | `products/clothing/shirts` | Ancestor slug segments followed by the current document's segment. |
| `_h_titlePath` | `Products/Clothing/Shirts` | Ancestor titles followed by the current document's title.          |

Set `admin.useAsTitle` to a field with a stable value. Use `slugField` if URL segments should come from a dedicated slug field rather than the title.

### Requesting Path Computation

Pass `computeHierarchyPaths: true` in the Local API context:

```ts
const page = await payload.findByID({
  collection: 'pages',
  id: pageID,
  overrideAccess: false,
  user,
  context: {
    computeHierarchyPaths: true,
  },
})
```

For REST requests, use the query parameter:

```http
GET /api/pages/abc123?computeHierarchyPaths=true
```

Paths are also computed when explicitly selected:

```ts
const page = await payload.findByID({
  collection: 'pages',
  id: pageID,
  overrideAccess: false,
  user,
  select: {
    title: true,
    _h_slugPath: true,
    _h_titlePath: true,
  },
})
```

Generated TypeScript types include the virtual path fields, but those fields may be absent at runtime unless path computation is requested. Regenerate your types after changing the configuration:

```bash
payload generate:types
```

### Performance

Computing paths fetches ancestors as needed and caches them within the request. The number of queries depends on tree depth and shared ancestors. Request paths when you need URLs or breadcrumbs; omit path computation for reads that do not use them.

Paths are computed from the current ancestor chain. Moving or renaming an item does not require rewriting stored paths on all descendants.

## Localization

The parent relationship is not localized, so tree structure is shared across locales. Titles can be localized. When the title field is localized, path computation uses the requested locale; reading with `locale: 'all'` returns paths by locale.

Publishing a changed parent affects the shared structure across locales. Account for this when publishing a single locale.

## Deleting Hierarchy Items

Deleting a hierarchy item also deletes its children in that collection. Payload clears references to the deleted items on related content documents, but keeps the content documents themselves.

For example, deleting a page with child pages deletes those pages too. Deleting a folder clears the folder assignment on its posts without deleting the posts.
