A file transformer is a small, ordered stage in Payload's upload pipeline. Transformers can:

- Process a file's bytes at upload time (resizing an image, converting a format, and so on)
- Serve a dynamically-transformed variant of an already-stored file at request time (for example, resizing an image on the fly based on query parameters)

Payload core owns transformer configuration, ordering, access control, and storage retrieval. Transformer packages own the actual byte manipulation. `@payloadcms/transformer-sharp` is Payload's official transformer, and covers the image-resizing behavior that shipped as part of core in Payload 3.x.

<Banner type="info">
  **Note:** If you only need Sharp-based image resizing at upload time — the
  same behavior Payload has always provided — see [Image
  Sizes](./overview#image-sizes) and [`@payloadcms/transformer-sharp`
  configuration](#payloadcmstransformer-sharp) below. You do not need to write a
  custom transformer for that.
</Banner>

## Configuring transformers

Transformers are configured once, globally, under `upload.transformers` in your Payload Config:

```ts
import { buildConfig } from 'payload'
import { sharpTransformer } from '@payloadcms/transformer-sharp'

export default buildConfig({
  collections: [
    /* ... */
  ],
  upload: {
    transformers: [sharpTransformer()],
  },
})
```

`upload.transformers` is the only transformer configuration surface — there is no per-collection or per-field transformer list. Each transformer decides, per request or per upload, which collections and MIME types it applies to.

Every transformer must declare a unique `slug`. Payload throws a startup error if two transformers share a slug, or if a transformer's `mimeTypes` array is empty.

### MIME patterns

A transformer's `mimeTypes` array accepts:

- An exact value, e.g. `image/png`
- A category wildcard, e.g. `image/*`
- The universal wildcard, `*/*`

## How the pipeline runs

For both upload-time and request-time processing, Payload builds a fixed, ordered list of eligible transformers before running any of them:

1. Filter to transformers that declare the capability being used (`transformFile` for uploads, `handleRequest` for dynamic requests).
2. Filter to transformers whose `mimeTypes` match the file's MIME type.
3. Call each remaining transformer's `canTransform` (if defined) to decide whether it's eligible for this specific file/request. A transformer with no `canTransform` is always eligible once it passes the MIME filter.

The result is a plan — a fixed list — computed before any transformer actually runs. Every eligible transformer then runs once, in the order it appears in `upload.transformers`, passing its result to the next:

- **`continue`** — hand the (possibly-replaced) file/response to the next transformer in the pipeline. Returning `continue` without a replacement preserves the same object reference; nothing is copied.
- **`complete`** — stop the pipeline here and use this result. No later transformer runs.
- **Throwing** — aborts the pipeline immediately. The error is logged and mapped to a `500` for dynamic requests; for uploads, no document is committed and no partial file is written.

Payload only ever keeps the current accumulator, never a history of every stage's output.

## The `canTransform` capability

```ts
canTransform: (args: {
  collectionSlug: string
  documentID?: number | string
  mimeType: string
  operation: 'request' | 'upload'
  req: PayloadRequest
}) => boolean | Promise<boolean>
```

`canTransform` must be inexpensive and side-effect-free — it must not fetch the file's source, call an external service, or perform the transformation itself. It only decides eligibility. If you omit it, the transformer is eligible for every request/upload that already passed the MIME filter.

## The `transformFile` capability (uploads)

```ts
transformFile: (args: {
  collectionSlug: string
  file: File
  options: unknown
  req: PayloadRequest
}) =>
  Promise<
    { file?: File; status: 'continue' } | { file: File; status: 'complete' }
  >
```

`transformFile` is a one-file-in, one-file-out primitive — it never writes to storage itself. Payload's upload pipeline calls every eligible transformer's `transformFile` in declaration order, threading the result of one into the next, then persists whatever the pipeline produces.

## The `handleRequest` capability (dynamic requests)

```ts
handleRequest: (args: {
  collectionSlug: string
  documentID: number | string
  filename: string
  getSourceFile: () => Promise<Response>
  mimeType: string
  req: PayloadRequest
}) =>
  Promise<
    | { response?: Response; status: 'continue' }
    | { response: Response; status: 'complete' }
  >
```

`getSourceFile` is a **lazy, single-use** getter for the stored file's bytes. It performs no work until called, and calling it a second time — including while the first call is still pending, or after it has rejected — throws. This means:

- A transformer that only redirects, or that answers from a source it already has, never has to pay the cost of reading the stored file.
- Once any transformer in the pipeline calls `getSourceFile`, no other transformer can call it again — the bytes are handed off exactly once.

Dynamic requests never write anything back to storage, and never trigger a document's own upload/delete hooks. A dynamic-transform request is a read-only view over an already-uploaded file.

### Example: a multi-stage local transformer

```ts
const uppercaseTextTransformer: UploadTransformer = {
  slug: 'uppercase-text',
  mimeTypes: ['text/plain'],
  canTransform: ({ req }) => req.searchParams?.has('uppercase') ?? false,
  handleRequest: async ({ getSourceFile }) => {
    const source = await getSourceFile()
    const text = await source.text()

    return {
      response: new Response(text.toUpperCase(), { headers: source.headers }),
      status: 'complete',
    }
  },
}
```

### Example: redirecting without fetching the source

A transformer that hands off to an external image-processing service never needs to read the stored file itself — it can `complete` with a redirect and skip `getSourceFile` entirely:

```ts
const externalResizeTransformer: UploadTransformer = {
  slug: 'external-resize',
  mimeTypes: ['image/*'],
  canTransform: ({ req }) => req.searchParams?.has('width') ?? false,
  handleRequest: async ({ collectionSlug, filename, req }) => {
    const width = req.searchParams!.get('width')

    return {
      response: Response.redirect(
        `https://images.example.com/${collectionSlug}/${filename}?w=${width}`,
        302,
      ),
      status: 'complete',
    }
  },
}
```

## Access control

Ordinary file reads are unaffected by transformers: they use the same collection `read` access control that governs every other file request.

A **dynamic-transform request** (one that at least one configured transformer is eligible for) additionally sets `req.fileTransform: true` for the duration of the single `access.read` call that decides whether the request may proceed. This lets a collection distinguish "someone is asking for a transformed variant of this file" from an ordinary read:

```ts
export const Media: CollectionConfig = {
  slug: 'media',
  access: {
    // Ordinary reads stay public; transformed variants require a signed-in user.
    read: ({ req }) => (req.fileTransform ? Boolean(req.user) : true),
  },
  upload: true,
}
```

`req.fileTransform` is `true` only during that one access-control call. It is not set during `canTransform`, `transformFile`, or `handleRequest`. If access is denied, the pipeline never runs — `getSourceFile`, every transformer's `handleRequest`, and any external service a transformer would have called are all skipped entirely.

This access check runs before any transformer executes, and before Payload resolves which storage adapter or external provider would serve the source bytes. A denied request never reaches storage.

<Banner type="warning">
  **Note:** This access-control lifecycle only applies to requests that go
  through Payload's file endpoint. A direct storage/CDN URL (for example, an S3
  bucket URL or a CDN-fronted URL returned by a storage adapter's
  `generateFileURL`) bypasses Payload entirely, including this access check. If
  you need every access to a file to be gated by Payload's access control, do
  not expose direct storage/CDN URLs for that collection.
</Banner>

## `@payloadcms/transformer-sharp`

`@payloadcms/transformer-sharp` is Payload's official Sharp-based transformer. Install it and register it once:

```sh
pnpm add @payloadcms/transformer-sharp
```

```ts
import { buildConfig } from 'payload'
import { sharpTransformer } from '@payloadcms/transformer-sharp'

export default buildConfig({
  upload: {
    transformers: [sharpTransformer()],
  },
})
```

### Upload-time image processing

Per-collection Sharp settings — `imageSizes`, `resizeOptions`, `formatOptions`, `trimOptions`, `constructorOptions`, `withMetadata`, `crop`, and `focalPoint` — are authored through `sharpTransformer({ collections })`, not on the collection's own `upload` config:

```ts
import { buildConfig } from 'payload'
import { sharpTransformer } from '@payloadcms/transformer-sharp'

export default buildConfig({
  collections: [
    {
      slug: 'media',
      upload: true,
      fields: [],
    },
  ],
  upload: {
    transformers: [
      sharpTransformer({
        collections: {
          media: {
            imageSizes: [
              { name: 'thumbnail', width: 400, height: 300 },
              { name: 'card', width: 768, height: 1024 },
            ],
            resizeOptions: {
              width: 2048,
              height: 2048,
              withoutEnlargement: true,
            },
          },
        },
      }),
    ],
  },
})
```

At startup, `sharpTransformer` writes a Sharp-agnostic projection of `imageSizes` (name, `admin`, and `generateImageName` only), `crop`, and `focalPoint` back onto the collection's sanitized `upload` config — so the Admin Panel, generated types, and the rest of core continue to see `collection.upload.imageSizes`/`.crop`/`.focalPoint` exactly as before. The `sizes` shape on your documents is unchanged.

See [Image Sizes](./overview#image-sizes) for what each Sharp-specific image size option does, and [Crop and Focal Point Selector](./overview#crop-and-focal-point-selector) for the Admin Panel behavior these settings control.

### Dynamic (request-time) resizing

`sharpTransformer` can resize a stored image on the fly when it's requested with recognized query parameters, without storing the resized result. This is **disabled by default**: until you enable it, resize parameters are ignored and the original file is served, exactly as in Payload 3.x.

Enable it with the `dynamic` option, either for every upload collection or only for the collections that need it:

```ts
// Every upload collection, with the default limits
sharpTransformer({ dynamic: true })

// Only the `media` collection
sharpTransformer({ dynamic: { collections: ['media'] } })
```

A slug in `dynamic.collections` that isn't an upload-enabled collection throws at startup. For collections that aren't listed, resize parameters are ignored and the original file is served.

Once enabled, request a file with any of these parameters:

```
GET /api/media/file/photo.png?width=400
GET /api/media/file/photo.png?height=300
GET /api/media/file/photo.png?width=400&height=300
GET /api/media/file/photo.png?width=400&withoutEnlargement=true
```

| Parameter            | Description                                                                              |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `width`              | Target width, in pixels. A positive integer.                                             |
| `height`             | Target height, in pixels. A positive integer.                                            |
| `withoutEnlargement` | `true` or `false`. Overrides the transformer's configured default for this request only. |

Recognized behavior:

- Presence of any recognized parameter routes the request through this transformer. Malformed values (a non-integer `width`, for example) return `400`, not a fallback to the original file.
- Repeated occurrences of the same parameter are invalid and return `400`.
- Unrelated query keys (`draft`, `depth`, `where`, `prefix`, and so on) are ignored — the request falls through as an ordinary read.
- Specifying both `width` and `height` crops to that exact box, centered (`fit: 'cover'`), by default.
- Specifying only one of `width`/`height` preserves the original aspect ratio.
- Images smaller than the requested size are upscaled by default. Pass `withoutEnlargement=true` to return the original size instead, or configure a different default (below).
- The output keeps the source image's own format — there is no `format`/quality query parameter in this version.
- The stored file's own MIME type governs whether it's eligible; unsupported types (for example, JPEG XL) are served unchanged, without error.
- `GET` and `HEAD` are both supported. A `Range` header on a recognized dynamic-resize request returns `416` — partial dynamic resizes are not supported.
- `prefix` is core-owned routing context, used to locate the stored document. It is never a resize parameter.

Passing an object enables dynamic resizing and configures the defaults for every dynamic-resize request on this transformer instance:

```ts
sharpTransformer({
  dynamic: {
    collections: ['media'], // omit to allow every upload collection
    fit: 'cover', // default
    position: 'center', // default
    maxWidth: 4096, // default
    maxHeight: 4096, // default
    maxPixels: 16_777_216, // default
    withoutEnlargement: false, // default
  },
})
```

As with every transformer, dynamic-resize output is never written back to storage — it is generated for that one response and discarded.

#### Securing dynamic resizing

Every dynamic-resize request decodes the full source image and encodes a new one, and the output is not cached. Anyone who can read a file can ask for it at any size within your limits, so on a publicly readable collection an unbounded stream of distinct sizes costs you CPU and memory on every request. Before enabling it, especially on public collections:

1. **Enable it only where it's needed.** Prefer `dynamic: { collections: [...] }` over `dynamic: true`.

2. **Restrict transformed reads in access control.** `req.fileTransform` is `true` while `access.read` decides whether a dynamic-transform request may proceed (see [Access control](#access-control)), and the request's query is available on `req.searchParams`. Use it to require a signed-in user, or to allow only the sizes your frontend actually uses:

   ```ts
   const allowedWidths = new Set(['320', '640', '1280'])

   export const Media: CollectionConfig = {
     slug: 'media',
     access: {
       read: ({ req }) => {
         // Ordinary reads are unaffected.
         if (!req.fileTransform) {
           return true
         }

         // Only a known set of widths, no arbitrary height or enlargement override.
         const width = req.searchParams.get('width')

         return (
           width !== null &&
           allowedWidths.has(width) &&
           !req.searchParams.has('height') &&
           !req.searchParams.has('withoutEnlargement')
         )
       },
     },
     upload: true,
   }
   ```

   A denied transform request returns `403`, and the source file is never fetched.

3. **Lower the limits to what you serve.** Set `maxWidth`, `maxHeight`, and `maxPixels` to your largest real rendition, and set `withoutEnlargement: true` so requests can't upscale small images. Limits apply per frame: animated GIF, WebP, and AVIF images are resized frame by frame, so a many-frame image costs far more than its dimensions suggest. If you accept animated uploads on a collection, keep its limits tight or leave dynamic resizing off for it.

4. **Cache the output in front of Payload.** Dynamic-resize responses don't set `Cache-Control`. Add one with the collection's [`modifyResponseHeaders`](./overview#modifying-response-headers), which also applies to dynamic-resize responses, and serve the endpoint through a CDN or reverse proxy that caches by full URL. A fixed set of allowed sizes (step 2) keeps the cache effective. Only mark responses `public` for collections whose files are publicly readable, or a shared cache will serve access-controlled files to anyone.

5. **Rate-limit at the edge.** Payload doesn't rate-limit file requests. If the endpoint is public, apply rate limits in your CDN, load balancer, or reverse proxy.

## `@payloadcms/transformer-cloudinary`

`@payloadcms/transformer-cloudinary` is a Cloudinary-backed transformer. Reach for it instead of (or alongside) `@payloadcms/transformer-sharp` when you want Cloudinary's content-aware features — `g_auto` smart cropping, `f_auto` format negotiation, `q_auto` quality — rather than local Sharp processing.

```sh
pnpm add @payloadcms/transformer-cloudinary
```

```ts
import { buildConfig } from 'payload'
import { cloudinaryTransformer } from '@payloadcms/transformer-cloudinary'

export default buildConfig({
  serverURL: 'https://example.com',
  upload: {
    transformers: [cloudinaryTransformer()],
  },
})
```

Credentials are read from the `CLOUDINARY_URL` environment variable (`cloudinary://<api_key>:<api_secret>@<cloud_name>`) by default. Pass `url` or `config` to override. They are resolved eagerly, so a misconfigured cloud fails at startup rather than on the first upload.

### How the source reaches Cloudinary#cloudinary-fetch

This transformer uses Cloudinary's [fetch delivery](https://cloudinary.com/documentation/fetch_remote_images): it builds an `image/fetch/` URL over the stored file's own URL and lets Cloudinary pull the source itself. It never calls `getSourceFile`, so the stored bytes never pass through Payload — and the single-use source handle stays available to any later transformer in the pipeline.

The source URL therefore **must be reachable from the public internet**, and its host must be allow-listed in your Cloudinary fetch settings.

By default the source URL is the requested file's own `url`, resolved against your config's `serverURL`. Override it when that isn't publicly reachable — a `localhost` dev server, for example, or a collection whose files are only served through Payload's access-controlled route:

```ts
cloudinaryTransformer({
  sourceURL: ({ filename }) => `https://cdn.example.com/media/${filename}`,
})
```

### Delivery mode#cloudinary-delivery

```ts
cloudinaryTransformer({ delivery: 'proxy' })
```

- `'proxy'` (default): Payload streams the bytes back from Cloudinary. Neither the Cloudinary URL nor the underlying source URL is exposed, and the response stays behind the collection's access control.
- `'redirect'`: Payload answers `302` with the Cloudinary URL. Cheapest — no bytes pass through Payload — but the transformed variant becomes publicly reachable and the source URL is disclosed to the client.

<Banner type="warning">
  **Note:** With `delivery: 'redirect'`, the transformed variant is served
  straight from Cloudinary's CDN, bypassing Payload's access control for every
  request after the redirect — the same caveat that applies to any direct
  storage/CDN URL.
</Banner>

### Dynamic (request-time) transformation#cloudinary-dynamic

Like `@payloadcms/transformer-sharp`, request-time transformation is **disabled by default**: resize parameters are ignored and the original file is served. Enable it for every upload collection or only the ones that need it:

```ts
cloudinaryTransformer({ dynamic: true })
cloudinaryTransformer({ dynamic: { collections: ['media'] } })
```

A slug in `dynamic.collections` that isn't an upload-enabled collection throws at startup.

Once enabled, this transformer recognizes the same `width`, `height`, and `withoutEnlargement` parameters as `@payloadcms/transformer-sharp`. Both share one file endpoint, so a URL should not mean different things depending on which transformer is installed. Cloudinary-specific settings are configured on the transformer rather than per request.

```
GET /api/media/file/photo.png?width=400
GET /api/media/file/photo.png?width=400&height=300
GET /api/media/file/photo.png?width=400&withoutEnlargement=true
```

Sharp's resize semantics map onto Cloudinary crop modes like this:

| Request                              | Cloudinary crop mode |
| ------------------------------------ | -------------------- |
| `width` + `height`                   | `c_fill`             |
| `width` or `height`                  | `c_scale`            |
| `width` + `height` + no enlargement  | `c_lfill`            |
| `width` or `height` + no enlargement | `c_limit`            |

Passing an object enables request-time transformation and configures the defaults for every dynamic request on this transformer instance:

```ts
cloudinaryTransformer({
  dynamic: {
    collections: ['media'], // omit to allow every upload collection
    crop: 'fill', // default, used when both width and height are given
    gravity: 'center', // default — 'auto' enables content-aware cropping
    quality: 'auto', // default
    format: undefined, // default (keep the source format); 'auto' negotiates per browser
    maxWidth: 4096, // default
    maxHeight: 4096, // default
    maxPixels: 16_777_216, // default
    withoutEnlargement: false, // default
  },
})
```

#### Securing dynamic transformation#cloudinary-securing

The same steps as [Securing dynamic resizing](#securing-dynamic-resizing) apply: enable it only for the collections that need it, restrict transformed reads with `req.fileTransform` in access control, and lower `maxWidth`, `maxHeight`, and `maxPixels` to your largest real rendition. The cost moves from your server to your Cloudinary account: every distinct size a client requests is a new derived asset, billed against your transformation and bandwidth quotas, and with `delivery: 'proxy'` the bytes also pass through Payload.

Two things are specific to Cloudinary:

- **With `delivery: 'redirect'`, Payload's limits only apply to the first request.** The Cloudinary URL the client is redirected to is unsigned, so a client can edit its transformation and request any other variant directly from Cloudinary, bypassing Payload's access control and limits. Use `'proxy'` if the limits matter.
- **Lock down fetch delivery in your Cloudinary settings.** Anyone who knows your cloud name can build fetch URLs, with or without Payload. Restrict the allowed fetch domains to the host your source files are served from. Cloudinary's _Strict transformations_ setting blocks edited transformations too, but because this transformer's URLs are unsigned, it also blocks every size you haven't explicitly allowed in the Cloudinary console — only enable it if you serve a fixed set of sizes and allow each one.

### Upload-time image processing#cloudinary-uploads

Per-collection settings are authored through `cloudinaryTransformer({ collections })`, not on the collection's own `upload` config:

```ts
cloudinaryTransformer({
  collections: {
    media: {
      crop: true,
      focalPoint: true,
      imageSizes: [
        { name: 'thumbnail', width: 400, height: 300 },
        // Cloudinary's content-aware crop — no local equivalent in Sharp
        { name: 'card', width: 768, height: 1024, gravity: 'auto' },
      ],
      resizeOptions: { width: 2048 },
      formatOptions: { format: 'webp', quality: 'auto' },
    },
  },
})
```

As with `sharpTransformer`, this writes a provider-agnostic projection of `imageSizes`, `crop`, and `focalPoint` back onto the collection's sanitized `upload` config at startup, so the Admin Panel, generated types, and the rest of core keep seeing `collection.upload.imageSizes` exactly as before. The `sizes` shape on your documents is unchanged, including the behavior where a size larger than the source in both dimensions is recorded with null metadata.

An Admin-selected crop becomes a `c_crop` step; a focal point becomes `g_xy_center` with the focus translated into source pixels.

<Banner type="info">
  **Note on cost and latency.** Cloudinary has no stateless "transform these
  bytes" API — every transformation is addressed against a stored asset.
  Upload-time processing therefore stages the original as a short-lived
  Cloudinary asset, generates all derived sizes in one call, pulls them back,
  and deletes the staged original before returning. If you only need local
  resizing, `@payloadcms/transformer-sharp` does it without the round trip.
</Banner>

Staged originals are written to `payload-transformer-tmp/`, configurable via `uploadFolder`. They are removed once the upload completes; a hard process crash mid-upload can leave one behind, so consider an auto-delete rule on that folder.

### Configuration Options#cloudinary-configuration

| Option         | Description                                                                               | Default                      |
| -------------- | ----------------------------------------------------------------------------------------- | ---------------------------- |
| `collections`  | Per-collection upload-time image processing settings                                      |                              |
| `config`       | Cloudinary client configuration                                                           |                              |
| `delivery`     | `'proxy'` or `'redirect'`                                                                 | `'proxy'`                    |
| `dynamic`      | Enables request-time transformation (`true` or an object with `collections` and defaults) | `false`                      |
| `slug`         | Transformer slug, unique across `upload.transformers`                                     | `'cloudinary'`               |
| `sourceURL`    | Overrides how the publicly reachable source URL is resolved                               | the requested file's `url`   |
| `uploadFolder` | Folder for short-lived upload-time originals                                              | `'payload-transformer-tmp'`  |
| `url`          | `cloudinary://<api_key>:<api_secret>@<cloud_name>`                                        | `process.env.CLOUDINARY_URL` |

## Non-goals

The transformer boundary intentionally does not include:

- **Caching.** Every dynamic-transform request re-runs the pipeline. A future version may introduce a cache-key insertion point ahead of `handleRequest` (derived from the collection, filename, and the recognized transform parameters), but no caching exists today.
- **CDN integration.** Transformers don't know about, and don't configure, any CDN in front of Payload. Serving transformed output through a CDN is entirely up to your own infrastructure.
- **A background jobs queue.** All transformation happens synchronously, in the request/upload path. A future version may accept a job-shaped input for expensive, queueable transforms, but no such queue exists today.

None of the above is implemented as a stub or a partial feature — they are simply not built yet.
