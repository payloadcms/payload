Your `PAYLOAD_SECRET` signs authentication tokens and encrypts any data you encrypt with
`payload.encrypt`. Rotating it — after a leak, or as part of a periodic key-rotation
policy — requires re-keying the data that was encrypted under the previous secret.

Payload provides the [`encrypt`/`decrypt`/`reencrypt`](#lower-level-utilities) primitives
to do this safely. The [`previousSecrets`](#previoussecrets) config keeps the old secret
accepted for reads during the rotation so it can be done with **zero downtime**.

## What a rotation affects

<Banner type="success">
  **Password logins and API keys keep working.** Passwords are hashed with a
  random per-user salt, and [API keys](./api-keys) are stored as a one-way hash.
  Neither involves `PAYLOAD_SECRET`, so a rotation does not affect logging in with
  a username/email and password, or authenticating with an API key.
</Banner>

- **JWT sessions** are signed with the secret. While the old secret is listed in
  `previousSecrets`, tokens signed under it still verify, so active sessions survive the
  rotation. Once you remove the old secret, those tokens stop verifying and users log in
  again.
- **API keys** are unaffected. They are stored as one-way hashes that derive nothing from the
  secret. Keys still held in the old encrypted format do not authenticate at all until
  [`migrateAPIKeysToHash`](./api-keys#upgrading-from-encrypted-keys) has been run, and once it
  has, a rotation has nothing left to do for them.
- **Encrypted values at rest** (any field you encrypt with `payload.encrypt`) can only be
  read while a secret that can decrypt them is in the keyring. A value whose secret is no
  longer present throws on read, so keep the old secret in `previousSecrets` until
  everything has been re-keyed.

## Procedure (zero-downtime)

1. Add the previous secret to `previousSecrets` while setting the new secret as the active
   `secret`, and deploy:

   ```ts
   export default buildConfig({
     secret: process.env.PAYLOAD_SECRET, // the new secret
     previousSecrets: [process.env.OLD_PAYLOAD_SECRET], // still accepted for reads
     // ...
   })
   ```

   New data is written under the new secret; existing sessions, API keys, and encrypted
   values keep working because the old secret is still in the keyring.

2. Re-key anything you encrypted yourself with `payload.encrypt`, using
   [`payload.reencrypt`](#lower-level-utilities) from inside a migration.

   If any API keys are still stored in the old encrypted format, convert them now with
   [`migrateAPIKeysToHash`](./api-keys#upgrading-from-encrypted-keys) — after which they no
   longer depend on any secret, and a future rotation will not involve them at all.

3. Once everything is re-keyed, **remove the old secret from `previousSecrets`** and deploy.
   Retiring it is what actually contains a leaked secret — do not keep old secrets in the
   keyring indefinitely.

## previousSecrets

`previousSecrets` is an array of prior `secret` values that Payload still accepts for
**reads** — verifying JWTs and decrypting stored values — during a bounded rotation. New data is always written with the active `secret`.

<Banner type="warning">
  A secret in `previousSecrets` is still accepted for auth: a leaked one can
  **forge tokens** and act as a user, and still decrypts data written under it.
  Re-key your data, then remove it promptly.
</Banner>

### Expiring a previous secret

Payload does not track an expiration for entries in `previousSecrets` — the array is read
as-is when the config is loaded. If you want a previous secret to stop being accepted after
a set window, gate it in your own config using a date you control, for example an
`OLD_PAYLOAD_SECRET_EXPIRATION` environment variable holding the date the secret was put
into rotation:

```ts
const oneMonth = 1000 * 60 * 60 * 24 * 30

// The date the previous secret was put into rotation, e.g. "2026-08-06".
const previousSecretAddedAt = process.env.OLD_PAYLOAD_SECRET_EXPIRATION
  ? new Date(process.env.OLD_PAYLOAD_SECRET_EXPIRATION).getTime()
  : 0

// Accept the previous secret only for one month after it was added.
const previousSecrets =
  process.env.OLD_PAYLOAD_SECRET &&
  previousSecretAddedAt > Date.now() - oneMonth
    ? [process.env.OLD_PAYLOAD_SECRET]
    : []

export default buildConfig({
  secret: process.env.PAYLOAD_SECRET,
  previousSecrets,
  // ...
})
```

<Banner type="warning">
  This check runs **once, when the config is loaded** (at startup / build), not
  continuously at runtime. A long-running server started while the secret was
  still valid keeps it in the keyring until the process restarts — the
  expiration only takes effect on the next boot or deploy. Trigger a restart /
  redeploy after the window if you need the old secret to actually drop out, and
  always re-key your data before the window closes so nothing is left readable
  only by the expired secret.
</Banner>

## rotateSecret

<Banner type="warning">
  **Deprecated.** `rotateSecret` existed to re-key API keys, which no longer derive anything
  from `PAYLOAD_SECRET`. It now delegates to
  [`migrateAPIKeysToHash`](./api-keys#upgrading-from-encrypted-keys), so an existing rotation
  migration keeps working — but call that directly instead. It throws if any key cannot be
  recovered, leaving those documents unchanged.
</Banner>

## Lower-level utilities

For data your own project encrypted with `payload.encrypt` (for example a custom
encrypted field), re-key it with `payload.reencrypt`, which decrypts with the old secret
and re-encrypts with the current one:

```ts
const next = payload.reencrypt(storedValue, {
  oldSecret: process.env.OLD_PAYLOAD_SECRET,
})
```

`payload.encrypt` and `payload.decrypt` also accept an explicit `{ secret }` to override
the key, where `secret` is the raw `PAYLOAD_SECRET` value:

```ts
const raw = payload.decrypt(storedValue, {
  secret: process.env.OLD_PAYLOAD_SECRET,
})
const next = payload.encrypt(raw)
```

<Banner type="warning">
  When migrating your own encrypted fields, read and write the stored values at
  the database layer (`payload.db.*`) rather than through the Local API. Field
  hooks that encrypt on write and decrypt on read would otherwise run with the
  current secret and corrupt data encrypted under the old one.
</Banner>

Unlike [`migrateAPIKeysToHash`](./api-keys#upgrading-from-encrypted-keys) — which verifies
every value it recovers, so it can be re-run safely — a hand-written `reencrypt` loop is
**not idempotent**, and has no equivalent way to tell an already-migrated value from a wrong
`oldSecret`. On a v1 value already re-keyed to the active secret it throws; on a legacy
AES-256-CTR value a wrong `oldSecret` does _not_ throw — it decrypts to garbage and silently
re-encrypts it. So don't guard by "decrypt under the current secret first" (unreliable for
legacy values): track which rows you have migrated, run the loop once, and pass the correct
`oldSecret`.

## Encryption format

New encrypted values use an authenticated envelope: `v1:<keyId>:<iv>:<authTag>:<ciphertext>`
(AES-256-GCM). The `keyId` is a non-secret fingerprint used to select the right key from the
keyring; the auth tag means a value encrypted under an unknown or wrong key **throws** on
decrypt rather than returning garbage. Values written by older versions of Payload
(AES-256-CTR, no prefix) are still read transparently and are upgraded to the v1 envelope
whenever they are re-encrypted.
