Folders group documents across collections and can nest inside other folders. In Payload 4, folders are a preset built on the [Hierarchy](../hierarchy/overview) foundation.

Define a collection with `folders: true`, then add `createFolderField` to the content collections it organizes. The folder collection stores the tree; each related document selects one folder.

<Banner type="info">
  Upgrading from Payload 3? The global `folders` configuration and the old
  per-content-collection opt-in have changed. See the [migration
  guide](../migration-guide/v4#folders-use-the-hierarchy-foundation).
</Banner>

## Quick Start

Create a folder collection and connect it to a content collection:

```ts
import type { CollectionConfig } from 'payload'

import { createFolderField } from 'payload'

export const Folders: CollectionConfig = {
  slug: 'folders',
  admin: {
    useAsTitle: 'name',
  },
  fields: [
    {
      name: 'name',
      type: 'text',
      required: true,
    },
  ],
  folders: true,
}

export const Posts: CollectionConfig = {
  slug: 'posts',
  fields: [
    {
      name: 'title',
      type: 'text',
      required: true,
    },
    createFolderField({ relationTo: 'folders' }),
  ],
}
```

Register both collections in your Payload config. To organize another collection in the same folders, add `createFolderField({ relationTo: 'folders' })` to that collection too.

Payload adds `_h_folders` as the parent relationship on the folder collection. The helper creates a relationship with the same name on posts. A folder can contain child folders and documents from the related collections.

## Folder Configuration

Set `folders` on the collection that stores folders. Use `true` for defaults or an object for customization:

```ts
folders: {
  collectionSpecific: true,
  joinField: {
    name: 'children',
  },
  parentFieldName: 'parentFolder',
}
```

The preset uses a folder icon, enables header-button parent selection by default, and sets `allowHasMany: false`. Its options are:

| Option                   | Description                                                                                                                     |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `parentFieldName`        | Parent relationship field name. Defaults to `_h_<collectionSlug>`. Related helper fields are renamed to match.                  |
| `collectionSpecific`     | Let folders restrict which related collections they accept. Defaults to `false`. Use `true` or `{ fieldName: 'allowedTypes' }`. |
| `joinField`              | Configure a join for direct child folders and assigned content, e.g. `{ name: 'children' }`.                                    |
| `slugField`              | Existing field used for slug path segments.                                                                                     |
| `slugify`                | Function used to slugify titles when `slugField` is not set.                                                                    |
| `slugPathFieldName`      | Virtual slug path field name. Defaults to `_h_slugPath`.                                                                        |
| `titlePathFieldName`     | Virtual title path field name. Defaults to `_h_titlePath`.                                                                      |
| `admin.injectSidebarTab` | Add a sidebar tab for this folder hierarchy. Defaults to `true`.                                                                |
| `admin.treeLimit`        | Maximum items to load in tree views. Defaults to `100`.                                                                         |
| `admin.useHeaderButton`  | Use a header button to select a parent folder. Defaults to `true`.                                                              |
| `admin.components.Icon`  | Override the folder icon.                                                                                                       |

Do not also set `hierarchy` or `tags` on the folder collection. The folder preset already enables hierarchy.

## Adding a Folder Field

Import `createFolderField` from `payload` and add its result to the content collection's `fields` array:

```ts
createFolderField({
  relationTo: 'folders',
  label: 'Folder',
  required: false,
})
```

| Option          | Description                                       |
| --------------- | ------------------------------------------------- |
| `relationTo` \* | Slug of the folder hierarchy collection.          |
| `label`         | Field label. Defaults to `'Folder'`.              |
| `required`      | Require a folder assignment.                      |
| `admin`         | Customize the relationship field's admin options. |

The helper creates an indexed, single relationship and adds a header button for folder selection. It generates the field name from `relationTo`; `name`, `type`, `relationTo`, and `hasMany` are managed by the helper.

For the default `folders` example, create a post with a folder assignment using `_h_folders`:

```ts
const post = await payload.create({
  collection: 'posts',
  overrideAccess: false,
  user,
  data: {
    title: 'Getting started',
    _h_folders: folderID,
  },
})
```

Use the configured `parentFieldName` instead if you override it.

## Shared Hierarchy Behavior

Folders support virtual breadcrumb paths, localized titles, collection restrictions, and optional joins through the hierarchy foundation. See [Hierarchy](../hierarchy/overview) for configuration and path computation.

Deleting a folder also deletes its child folders. The hierarchy hooks clear folder references on related content documents without deleting those content documents.

For multiple taxonomy assignments, use [Tags](../tags/overview). A content collection can have both folder and tag fields referencing separate hierarchy collections.
