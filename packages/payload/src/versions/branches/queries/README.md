The internal branch query boundary reads the effective content relation with original collection read access. `queryBranchContentGraph` automatically collects a bounded raw forward graph, including authorized positive and denied or missing negative relationship entries. Root selection, full raw content, typed logical IDs, joins, counts and referenced ordinary documents finish inside the adapter's consistent read boundary. Outer population and field/document hooks may consume the frozen graph only after validation succeeds. An unknown graph key throws; population must never fall through to a new database read.

The graph follows configured relationship, upload, join, group, tab, array, block and locale fields. JSON and rich text remain opaque. Depth respects the configured Payload maximum (ten by default) and field maximum depth. The M4/M11 population integration must add rich-text editor-specific relationship discovery before editor afterRead population can consume this graph; opaque JSON/editor bodies are not inferred as generic relationships. The graph is private to one operation, including its branch, locale/fallback and access context. Its finite budget is 10,000 distinct typed document coordinates and 16 MiB of raw documents and coordinate keys. Adapter optimistic traces additionally bound statements, SQL/parameter size and raw result bytes. Exceeding any bound fails before outer content or hooks escape; it never silently truncates the graph.

PostgreSQL-owned reads use repeatable read. Existing repeatable-read or serializable caller transactions retain their own native snapshot. Existing default read-committed callers retain their transaction and read their own writes: their exact SQL, parameters and complete ordered raw results must recur together in one final native PostgreSQL statement snapshot. No callback or hook is replayed. D1 uses the analogous bounded trace but validates through one actual atomic binding batch. MongoDB-owned reads use a driver snapshot session pinned by a bounded native control read before any access callback; subsequent reads carry the same `atClusterTime`. Existing MongoDB caller transactions must have snapshot and majority concerns; the experimental branch opt-in supplies omitted native transaction defaults while preserving explicit choices. A read snapshot never supplies mutation transaction capabilities.

Access callbacks are trusted server code and can explicitly invoke nested Local API operations. Those explicit nested reads currently retain legacy document/draft selection; selected-branch Local API routing is M4 work. Their native reads are coherent at this snapshot, and their ordinary hook semantics remain: their hooks run once, and their database reads remain inside the scoped snapshot or trace. The outer raw graph does not replay callbacks or nested hooks if validation later conflicts, and it does not promise exactly-once external effects for trusted callback code. This differs from automatic outer population: its hooks remain deferred until the raw graph validates. Captured original Payload arrow methods retain the trusted scoped Payload during Local API normalization. Native Request accessors keep their branded receiver without cloning, teeing or reading the body, and the operation gets a fresh loader instead of inheriting an earlier request cache.

The supplied Payload and database capabilities are immutable and expire when the raw callback completes or fails. They expose bound read entrypoints only; native driver handles, mutation methods, job APIs and atomic write batches are unavailable. Captured scoped read methods inject the trusted request when omitted and reject invocation after the scope closes. Request normalization creates registered private forks; manually copied/spread or stashed partial requests carrying a scoped Payload are rejected instead of detaching into an ordinary connection. Intentional ambient operations through a separately captured original Payload remain separate operations. M4 outer hooks and write stages must receive the original operation request, never the expired raw read view.

The read-only callback must not mutate the same caller transaction through an independently captured ambient handle. Repeatable-read and Mongo snapshot transactions see their own writes, so such interleaving is outside this frozen-read contract. The original caller may write before or after the raw callback; separate committed concurrent transactions are handled by the snapshot or final atomic trace validation.

MongoDB `allowAdditionalKeys: true` remains on the legacy versions/drafts route. Experimental branch query registration rejects that mode before composing or indexing content, because undeclared root/row keys do not yet have an authoritative scope-ownership contract. This is a temporary admission boundary, not permission to omit existing data during upgrade. M4/M8 must preserve schema-complement values (including localized container ownership and opaque values), and M9 must rehearse migration from the actual released native behavior before activation.

A scalar compatibility status treats untranslated absent/absent locale heads as neutral. It requires live shared content, matching current live selections and, when the schema contains localized content, at least one live locale head. A missing all-locale publication, differing selection, withdrawal or structural conflict remains draft. Localized status maps retain draft for an absent locale; translated field completeness is independent of published-head availability.

Polymorphic reverse joins choose one common union order before paging: explicit request sort, join field default, agreeing effective target defaults, common descending createdAt when every target has timestamps, or ascending logical ID. A single target keeps its collection default/fallback. Native ties use typed logical IDs before per-target truncation and relationTo for equal polymorphic identities. This gives one stable page order rather than independently truncating incompatible target orders.

The raw localized status map includes every configured locale. Released public serializers can differ: ordinary SQL reads may omit an untranslated locale status while MongoDB defaults it to draft. M4 must preserve actual legacy locale-specific response shapes when routing public reads; M9 must cover these untranslated source states during migration.
